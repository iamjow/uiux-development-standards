# Validation Rubric

Shared by every agent in the UIUX validation team. The two standards documents define the rules. This rubric defines how violations are graded, recorded, and turned into a verdict.

- **Dev** = `uiux-development-standard.md`
- **Review** = `uiux-code-review-standard.md`

---

## 1. Ground rules

1. Only flag rules that exist in Dev or Review. Do not import other style guides. WCAG 2.2 AA success criteria not spelled out in Dev §10 may be cited by number, because Dev §10 requires WCAG 2.2 AA conformance.
2. Read-only. Never create, edit, move, or delete files in the target project. Never install dependencies or run the project's scripts.
3. Every finding needs evidence: a `path:line` relative to the target root and the exact code quoted from that line. Read the surrounding code before reporting. A grep hit alone is not evidence.
4. Apply the "Do not flag" lists in each Review section and Review §25 (Avoid False Positives) before reporting. For wrapper, `div`, class, and ARIA findings, record which purpose you looked for and did not find.
5. One finding per root cause. Group repeated instances of the same rule with the same fix into one finding. List up to 10 locations and give the total count.
6. When you cannot decide from static code, do not guess. Record the rule as `MANUAL` (needs a runtime or visual check) or `CONFIRM` (needs an answer from the delivering team).

### Files to skip

`node_modules/`, `dist/`, `build/`, `.next/`, `.nuxt/`, `.output/`, `.svelte-kit/`, `vendor/`, `coverage/`, `.git/`, `*.min.js`, `*.min.css`, `*.map`, lockfiles, tests (`*.spec.*`, `*.test.*`, `__tests__/`, `e2e/`, `cypress/`), and Storybook stories (`*.stories.*`).

## 2. Interpretations for delivered projects

The delivered project is a **new project**. Every dependency and pattern in it was introduced by the generation, so:

- Exceptions that depend on "the project already uses / already depends on" (Dev §1 allowed exceptions, Review §21) do not auto-pass. Record a third-party component library as `CONFIRM` unless it is on the Dev §1 banned list.
- Framework-native scoped SCSS (`<style scoped lang="scss">`, `*.module.scss`) is accepted in a framework project, provided tokens and breakpoint mixins come from the shared `_variables.scss` and `_mixins.scss`. A framework `<style>` without `lang="scss"` is plain CSS and violates Dev §1.
- BEM separators (`block__element--modifier`) count as kebab-case when each part is kebab-case.
- Stable IDs from a framework helper (`useId()`) used for label or ARIA association are not "random or autogenerated" under Dev §6. Hard-coded meaningless IDs (`id="frame-12"`, `id="div-3"`) are.
- Design-export artifacts count as autogenerated names under Dev §6: classes or IDs such as `frame-123`, `group-4`, `rectangle-2`, `text-wrapper-5`, `div-2`, `overlap-group`, hashed names such as `css-1x2y3z` or `sc-abc123`.

## 3. Severity

Severity follows Review §23: user impact first. Dev-standard rules carry no direct user impact but are acceptance requirements, so they use the mapping below.

| Severity | Use for |
|---|---|
| **Critical** | Everything in the Review §23 Critical list. |
| **High** | Everything in the Review §23 High list, plus these Dev-standard violations: a banned framework, library, or CSS-in-JS (Dev §1); authored plain CSS instead of SCSS (Dev §1, §4); static `style` attributes, embedded `<style>` blocks, inline event handlers, embedded `<script>` code, or `javascript:` URLs (Dev §1, §12, Review §20); raw color or font-family literals outside `_variables.scss` (Dev §9); brand tokens redefined outside `_variables.scss` (Dev §9); no `_variables.scss` (Dev §4, §9); all component and layout styles in one file (Dev §4); no responsive rules at all (Dev §8); missing visible focus indicator (Dev §10); text contrast below Dev §10 thresholds; a feature outside the browser target with no fallback (Dev §13); `innerHTML` with interpolated data. |
| **Medium** | Everything in the Review §23 Medium list, plus: duplicated CSS or markup that should share a component (Dev §4, §5, §11); a repeated UI pattern not extracted into a component (Dev §5); non-kebab-case or autogenerated class names, random IDs, IDs used for styling (Dev §6, Review §6); layout styles not under `layouts/` (Dev §7); raw media queries instead of shared breakpoint mixins, or media queries inside component, layout, or page partials instead of the `responsive/` folder (Dev §4, §8); raw spacing, font-size, radius, or shadow values outside `_variables.scss` (Dev §9); `px` for type or spacing instead of `rem` (Dev §10); non-essential animation not wrapped in `prefers-reduced-motion` (Dev §10); framework project manipulating the DOM directly for behavior the framework should own (Dev §12); browserslist config that differs from the Dev §13 target. |
| **Low** | Everything in the Review §23 Low list. |

Literal-value exceptions for Dev §9: `0`, `auto`, `none`, `inherit`, `initial`, `unset`, `transparent`, `currentColor`, `100%`, `50%`, and any value computed from a token (`$space-md * 2`, `rgba($color-black, 0.5)`, `color.adjust($color-primary, ...)`, `var(--token)`). Border widths are not tokens under Dev §9.

## 4. Output Requirements gate (Dev §14)

Every finding maps to exactly one primary requirement from R1–R13. R14 and R15 are derived; never map a finding to them.

| ID | Requirement | Typical sources |
|---|---|---|
| R1 | Use HTML5 | doctype, charset, obsolete elements and attributes |
| R2 | Use SCSS | Dev §1, §4 |
| R3 | Use semantic HTML | Dev §2, Review §1–4, §13, §14 |
| R4 | Use reusable components | Dev §5, §11 duplicate markup |
| R5 | Separate HTML, SCSS, and JavaScript | Dev §1 inline styles, §12, Review §20 |
| R6 | Follow the SCSS architecture | Dev §4, §7 |
| R7 | Use centralized design tokens | Dev §9 |
| R8 | Colors and fonts easy to update | Dev §9 brand tokens, theme structure |
| R9 | Support desktop, tablet, and mobile | Dev §8 |
| R10 | Use the project's framework for behavior | Dev §12 |
| R11 | Meet the browser support target | Dev §13 |
| R12 | Follow the Markup Quality rules | Dev §3, Dev §6, Review §5–8, §12, §15, §16, §18 |
| R13 | Conform to WCAG 2.2 AA | Dev §10, Review §9–11, §17, §19 |
| R14 | Be maintainable and scalable | Derived |
| R15 | Be production-ready | Derived |

Status per requirement:

- **FAIL**: at least one Critical or High finding is mapped to it.
- **CONFIRM**: no blocking finding, but at least one open `CONFIRM` item.
- **PASS**: anything else. Medium and Low findings are listed but do not fail the requirement.
- **R8** also fails when a High finding for raw color or font-family literals is mapped to R7, because a reskin from `_variables.scss` alone cannot reach those elements.
- **R14** fails when R4, R6, or R7 fails.
- **R15** fails when any Critical finding exists or any of R1–R13 fails.

### Verdict

- **FAIL**: any Critical or High finding.
- **PASS WITH NOTES**: no Critical or High, but Medium or Low findings or open `CONFIRM` items exist.
- **PASS**: no findings and no open `CONFIRM` items.

## 5. Specialist output format

Return exactly three sections, in this order.

### Context

Framework, styling setup, entry points, and any assumption you made. Keep it to five lines or fewer.

### Coverage

One row per rule in your scope.

| Rule | Status | Note |
|---|---|---|
| Dev §10 Skip link | PASS | `index.html:14` |
| Dev §10 Contrast | MANUAL | Two text/background pairs set at runtime |

Status values: `PASS`, `FAIL`, `N/A`, `MANUAL`, `CONFIRM`.

### Findings

One block per finding, using your prefix (`STACK`, `SCSS`, `MARKUP`, `A11Y`) and a running number.

````markdown
#### A11Y-3 · Critical · Icon-only cart button has no accessible name
- **Rule:** Dev §3 Markup Quality; Review §10 Icon Accessibility
- **Requirement:** R13
- **Location:** `src/components/header.html:42` (+2 more: `src/pages/cart.html:18`, `src/pages/product.html:61`)
- **Evidence:**
  ```html
  <button type="button" class="header-cart"><svg>...</svg></button>
  ```
- **Finding:** The button contains only an SVG, so screen readers announce it as "button" with no name.
- **Why:** Users of assistive technology cannot tell what the control does.
- **Recommendation:**
  ```html
  <button type="button" class="header-cart" aria-label="Cart">
    <svg aria-hidden="true" focusable="false">...</svg>
  </button>
  ```
- **Purpose checked:** n/a
- **Confidence:** high
````

Confidence is `high` when the evidence alone proves the violation and `medium` when it depends on context you could not fully trace. Say what would settle a `medium` finding.

If there are no findings, write `No findings.` under the heading.
