# Validate a delivered project against the UIUX standards

You are the orchestrator. Specialists find violations, and you merge them into one report. Do not do the specialists' checks yourself.

Target: `$ARGUMENTS`

## 1. Resolve inputs

1. If no target path was given, ask for it and stop.
2. Resolve to absolute paths:
   - `TARGET`: the delivered project.
   - `DEV`: `uiux-development-standard.md` at the root of this repo.
   - `REVIEW`: `uiux-code-review-standard.md` at the root of this repo.
   - `RUBRIC`: `.claude/skills/validate-uiux/rubric.md` in this repo.
3. Confirm all four exist. Read `RUBRIC` in full; you apply sections 3 and 4 yourself in step 5.
4. Record versions for the report: the commit of `TARGET` (`git -C "$TARGET" rev-parse --short HEAD`, or "not a git repository") and the commit of this repo, so the report says which delivery was checked against which version of the standards.

## 2. Scan the project

Scan the project with read-only commands and write a short summary. Skip the folders listed in rubric §1.

- Project name (from `package.json` `name`, otherwise the folder name).
- Framework: Vue, Nuxt, React, Next, Svelte, Angular, Laravel Blade, or plain HTML. Base it on dependencies and file types.
- File counts by type: `.html`, `.vue`, `.jsx`/`.tsx`, `.blade.php`, `.scss`, `.css`, `.js`/`.ts`.
- Entry points: HTML shell, JS entry, SCSS entry.
- Any handoff notes from the delivering team (`README`, `HANDOFF`, `NOTES` files). Specialists use them to resolve `CONFIRM` items.

## 3. Run the specialist team

Launch all four in a single message so they run concurrently, and give each the name in the table. This project enables agent teams (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` in `.claude/settings.json`), so named agents start as **teammates**. Without that setting, or in a non-interactive session, they run as ordinary subagents, and this step works the same way.

| Name | Agent type | Covers |
|---|---|---|
| `stack` | `uiux-stack-validator` | Tech stack, separation, JavaScript, browser support |
| `scss` | `uiux-scss-validator` | SCSS architecture, layout files, responsive, design tokens, duplicate CSS |
| `markup` | `uiux-markup-validator` | Semantic HTML, structure, headings, classes, IDs, controls, component reuse |
| `a11y` | `uiux-a11y-validator` | WCAG 2.2 AA, forms, ARIA, keyboard, focus, contrast |

Agent budget: these four only. Do not spawn more teammates or subagents. Wait for all four to report before merging, and don't do their checks yourself.

Give each the same prompt, filled in:

```text
Validate the project at TARGET against your slice of the UIUX standards.

Standards: DEV, REVIEW
Rubric: RUBRIC
Framework: <framework>
Project scan:
<scan summary>

Follow your agent instructions and return Context, Coverage, and Findings in the rubric §5 format. Read-only: do not modify anything under TARGET.

Your teammates are stack, scss, markup, and a11y. If you find a problem that belongs to another teammate's slice, send it to that teammate in one short message instead of reporting it yourself. Report once, then stop.
```

When all four have reported, ask each teammate to shut down ("Ask the stack teammate to shut down", and so on). An idle teammate keeps using tokens until it exits.

New agent files usually register within seconds, but the first file in a new `agents/` directory needs a session restart, and registration can lag. If a `subagent_type` is not found, launch `general-purpose` instead and start its prompt with: `Your agent instructions are in <absolute path to .claude/agents/prototype-validation/<name>.md>. Read that file first and follow it exactly. Read-only: never write or edit files.`

## 4. Merge

1. Collect every finding.
2. Deduplicate: two findings with the same location and the same root cause become one. Keep the higher severity, list both rules, keep the clearer recommendation.
3. Collect every `CONFIRM` and `MANUAL` coverage row.

## 5. Decide

Apply rubric §4: compute R1–R15, then the verdict.

## 6. Write the report

Write to `validation-reports/<project-name>-<YYYY-MM-DD>.md` in this repo. If the file exists, add `-2`, `-3`, and so on. Never write into `TARGET`.

Renumber findings `F-1`, `F-2` ... in severity order, keeping the specialist prefix in parentheses, for example `F-4 (A11Y-3)`.

```markdown
# UIUX Standards Validation: <project-name>

| | |
|---|---|
| **Verdict** | FAIL / PASS WITH NOTES / PASS |
| Target | `<TARGET>` @ `<commit>` |
| Framework | <framework> |
| Standards | `uiux-development-standard.md`, `uiux-code-review-standard.md` @ `<standards commit>` |
| Date | <YYYY-MM-DD> |

## Summary

<Two or three sentences: verdict, the main reasons, what must change before acceptance.>

| Critical | High | Medium | Low | Needs confirmation | Manual checks |
|---|---|---|---|---|---|
| n | n | n | n | n | n |

## Output Requirements (Dev §14)

| ID | Requirement | Status | Findings |
|---|---|---|---|
| R1 | Use HTML5 | PASS | — |
| ... | | | |

## Blocking findings (must fix before acceptance)

<Critical, then High, each in the rubric §5 format without the Confidence line.>

## Non-blocking findings

<Medium, then Low.>

## Needs confirmation from the delivering team

<Each CONFIRM item: what to confirm and why it matters.>

## Manual checks

<Each MANUAL item: what to check in a browser or with a screen reader, and how.>

## Coverage

<One table per specialist, from their Coverage sections.>
```

## 7. Reply

Reply in five lines or fewer: the verdict, the count by severity, the top three blocking findings by title, and a link to the report.
