# UIUX Development Standards

## Objective

Generate a production-ready frontend implementation that follows the UI/UX development standards.

The generated output should require minimal manual cleanup and be ready for implementation.

---

## 1. UI Technology Standards

Use the following technologies for UI implementation:

- HTML5
- SCSS
- JavaScript

These standards apply to new projects and to new UI built in a project that has no established styling stack. They apply regardless of the frontend framework (Vue, React, Blade, plain HTML).

In a project with an established styling stack, follow that stack and the project's conventions instead of introducing a second one.

Do NOT introduce:

- Tailwind CSS
- Bootstrap
- Bulma
- Material UI
- Foundation
- CSS-in-JS libraries
- Inline styles, embedded `<style>` blocks, or HTML `style` attributes

Allowed exceptions:

- Framework-native scoped styles (Vue `<style scoped lang="scss">`, CSS Modules) when the project already uses them
- Dynamic style bindings for values computed at runtime, such as a drag position, a progress width, or a CSS custom property set from data
- Third-party component libraries the project already depends on

---

## 2. HTML Standards

Use semantic HTML5.

Use semantic elements when they match the content:

- `header`
- `nav`
- `main`
- `section`
- `article`
- `aside`
- `footer`
- `form`
- `button`
- `table`
- `ul`
- `ol`
- `select`
- `details` / `summary`

Requirements:

- Clean DOM structure
- No unnecessary wrapper elements
- Proper heading hierarchy
- Accessible markup (see Accessibility)
- Logical element grouping

A wrapper is unnecessary when removing it changes no rendered output, no selector or script targets it, and it is not a framework component root or slot container.

---

## 3. Markup Quality

These rules mirror the UIUX Code Review Standard. Generated markup will be reviewed against them.

- Use `<button>` for actions and `<a href>` for navigation. Never make a `div` or `span` clickable.
- Every `<button>` inside a form has an explicit `type`. Default to `type="button"`; use `type="submit"` only for the submit action.
- Every `<img>` has `alt`. Meaningful images describe content or purpose. Decorative images use `alt=""`.
- Icon-only controls have an accessible name through `aria-label` or visually hidden text. Icon SVGs carry `aria-hidden="true" focusable="false"`.
- Every form control has a visible `<label for>` matching a unique `id`. Placeholder is not a label.
- Use the native input type that matches the data: `email`, `password`, `search`, `tel`, `url`. Use `type="number"` only for quantities; use `inputmode="numeric"` with a `pattern` for codes and identifiers. Do not use `type="date"` unless the project uses native date inputs.
- Content that is a list uses `ul` or `ol`. Tabular data uses `table` with `caption`, `thead`, `tbody`, `th scope`.
- No `<br>` for spacing. No empty elements for spacing. Spacing comes from SCSS.
- Do not add ARIA that duplicates native semantics. Never add `role="button"` or `aria-label` to a native `<button>` with visible text.
- Prefer native HTML (`button`, `a`, `input`, `select`, `details`/`summary`, `dialog`) over custom implementations unless the design requires behavior native elements cannot provide.

## 4. SCSS Standards

All styling must be written using SCSS.

Use a reusable SCSS architecture. Example for a plain HTML project:

```text
styles/
  app.scss
  _variables.scss
  _mixins.scss
  _global.scss
  components/
    _button.scss
    _card.scss
    _table.scss
    _form.scss
    _modal.scss
    _navigation.scss
  layouts/
    _header.scss
    _footer.scss
    _sidebar.scss
    _content.scss
  pages/
    _dashboard.scss
    _settings.scss
    _profile.scss
  responsive/
    _tablet.scss
    _mobile.scss
```

Component, layout, and page partials hold the desktop (base) rules only. All responsive styles live in `responsive/`, one partial per breakpoint (`_tablet.scss`, `_mobile.scss`, plus any extra breakpoint the project defines), each wrapping its overrides in the matching breakpoint mixin from `_mixins.scss` and grouped by component in the same order as the component partials. `app.scss` imports `responsive/` last so the overrides win by order, not by specificity. Do not write media queries inside component, layout, or page partials.

Avoid placing all styles inside one file.

Avoid duplicate styling. Shared components share the same SCSS.

---

## 5. Component Standards

Create reusable components for UI patterns that appear more than once or are clearly part of a design system.

Examples:

- Buttons
- Cards
- Forms
- Inputs
- Dropdowns
- Tables
- Tabs
- Badges
- Alerts
- Modal
- Pagination

Layouts (Header, Sidebar, Footer, Navigation) are not components. See Layout.

---

## 6. Naming Convention

Use kebab-case.

Examples:

```text
customer-card
order-table
user-profile
```

Use meaningful names. Avoid autogenerated class names.

Use IDs only for functional purposes, such as associating a label with a form control or an in-page anchor. Never use random or autogenerated IDs.

---

## 7. Layout

Keep layouts modular.

Separate:

- Header
- Sidebar
- Main Content
- Footer

Each layout has its own SCSS file under `layouts/`.

---

## 8. Responsive Design

Support desktop, tablet, and mobile by default. When the project supplies breakpoints or responsive requirements, follow them exactly.

Use responsive SCSS through shared breakpoint mixins, written in the `responsive/` partials described in section 4, never inside component, layout, or page partials.

Avoid duplicated layouts.

Prefer flexible layouts using:

- Flexbox
- CSS Grid

---

## 9. Design Tokens

Design tokens are SCSS variables defined in `_variables.scss`.

All colors, fonts, spacing, border radius, shadows, and other reusable design values must be defined as design tokens.

Do not use raw color or font literals inside component or layout styles. Every such value comes from `_variables.scss`.

Maintain consistent:

- spacing
- typography
- border radius
- colors
- shadows
- alignment

The project must be structured so that branding or theme changes can be made from `_variables.scss` with minimal code changes.

## 10. Accessibility

All generated UI must conform to WCAG 2.2 Level AA. Form, image, and ARIA rules are in Markup Quality.

Document and structure:

- Set `lang` on `<html>`.
- Use landmarks: one `main`, plus `header`, `nav`, `footer`, `aside` as applicable. Name repeated landmarks (`<nav aria-label="Footer">`).
- Add a skip link to `main` as the first focusable element.

Color and focus:

- Contrast: text 4.5:1, large text 3:1, UI component boundaries and focus indicators 3:1.
- Never convey state, error, or meaning by color alone.
- Keep a visible focus indicator. Never write `outline: none` without a `:focus-visible` replacement of at least 3:1 contrast.

Keyboard:

- Every control is reachable with Tab in DOM order.
- Never use `tabindex` greater than 0.
- Custom controls need a `role`, `tabindex="0"`, and key handlers. Prefer native elements first.
- No keyboard traps. Modals trap focus while open, close on Escape, and return focus to the opener.

Forms:

- Group radio and checkbox sets with `fieldset` and `legend`.
- Mark required fields with `required` and explain the indicator in text.
- Add `autocomplete` to identity fields (name, email, tel, address).
- Errors: show the message as text, set `aria-invalid="true"`, link the message with `aria-describedby`, and announce it with `role="alert"` or by moving focus to the first invalid field.

Dynamic content and motion:

- Alerts, toasts, and status updates use `role="status"` (polite) or `role="alert"` (assertive).
- Wrap non-essential animation in `@media (prefers-reduced-motion: no-preference)`.

Size and zoom:

- Interactive targets are at least 24x24 CSS px; 44px for primary touch actions.
- Never set `user-scalable=no` or `maximum-scale` on the viewport meta.
- Use `rem` for type and spacing. Layouts reflow at 320px width without horizontal scroll.

Component contracts (WAI-ARIA Authoring Practices):

- Dropdown menu: trigger has `aria-expanded` and `aria-controls`; Arrow keys move between items; Escape closes and returns focus. Use native `<select>` for simple choice.
- Tabs: `role="tablist"`, `tab`, `tabpanel`; `aria-selected` and `aria-controls` on tabs; Left/Right arrows move between tabs; only the active tab is in the Tab order.
- Modal: use `<dialog>` with `showModal()`, or `role="dialog" aria-modal="true"`; name it with `aria-labelledby`; trap focus, close on Escape, restore focus.
- Alerts: `role="alert"` for errors, `role="status"` for confirmations; the dismiss button has an accessible name.
- Pagination: `<nav aria-label="Pagination">` with a list of links; current page has `aria-current="page"`; disabled prev/next are `<button disabled>` or omitted, not dead links.

## 11. Performance

Avoid:

- duplicate HTML
- duplicate CSS
- deeply nested elements
- unnecessary wrappers

Keep markup clean and maintainable.

---

## 12. JavaScript

Keep JavaScript separate from HTML. Do not embed scripts inside HTML.

Use the project's framework for behavior. Write framework-free JavaScript only when no framework is in use.

Keep functionality modular.

---

## 13. Browser Support

Target the following browserslist:

```text
defaults, not IE 11
```

Do not use features that fall outside this target without a fallback.

---

## 14. Output Requirements

The generated project must:

- [ ] Use HTML5
- [ ] Use SCSS
- [ ] Use semantic HTML
- [ ] Use reusable components
- [ ] Separate HTML, SCSS, and JavaScript
- [ ] Follow the SCSS architecture described in SCSS Standards
- [ ] Use centralized design tokens for colors, fonts, and other theme values
- [ ] Make colors and fonts easy to update for future reskin or branding changes
- [ ] Support desktop, tablet, and mobile
- [ ] Use the project's framework for behavior, with framework-free JavaScript only when no framework is in use
- [ ] Meet the browser support target
- [ ] Follow the Markup Quality rules
- [ ] Conform to WCAG 2.2 AA as described in Accessibility
- [ ] Be maintainable and scalable
- [ ] Be production-ready

## 15. Design Fidelity Tolerance

This section defines what "matches the design" means when an implementation is validated against its Figma source. It is the pass/fail rule for the fidelity gate, and it is applied before code review.

A delta is **blocking** when it changes what a user sees or can do. A delta is **minor** when it is within the tolerances below. The implementation matches the design only when there are zero blocking deltas.

| Category | Rule | Blocking when |
|---|---|---|
| Tokens | Every color, font, radius, and shadow resolves to a token in `_variables.scss`. The token's value equals the Figma value. | A raw literal is used, or a token value differs from Figma |
| Typography | Family, weight, size, and line height match the Figma text style at each breakpoint. | Any of the four differs |
| Spacing and sizing | Padding, margin, gap, and fixed dimensions are within 2px of Figma, to allow rounding. | Difference exceeds 2px, or an element's size class changes (fixed to fluid, or the reverse) |
| Layout | Element order, alignment, and wrapping match Figma at desktop, tablet, and mobile. | Order, alignment, or wrapping differs at any breakpoint, or an element present in Figma is missing |
| States | Every state present in Figma is implemented: hover, focus, active, disabled, error, empty, loading, selected. Focus must be visible. | Any Figma state is missing or not visible |
| Interactions | Every prototype reaction recorded in the spec's Interactions table is implemented: the same trigger (click, hover, press, drag, key, timeout) on the same control navigates to, opens, swaps, or changes to the same destination. Overlays anchor at the Figma offset from their trigger, within 2px. Transitions keep Figma's type and duration, inside the reduced-motion media query. A `CHANGE_TO` state renders the variant's values. | A wired trigger does nothing, fires on a different trigger, or reaches a different destination; an overlay anchors more than 2px off; a transition's type or duration differs from Figma, or a Figma transition is missing |
| Assets | Icons and images are the ones in Figma, at the Figma size, with the decorative or meaningful treatment the spec records. | A different icon is used, or a meaningful image lacks alt text |
| Content | Placeholder copy may differ from Figma. Real labels, headings, and button text must match. | A label, heading, or control text differs in meaning |

Rules for the validator:

- Compare against the design spec and the Figma frame, not against the builder's description of the work.
- Where Figma does not define a breakpoint or state, that is a spec gap, not a fidelity failure. Record it separately. A control with no prototype wiring is a spec gap of the same kind; a control with wiring that the build ignores is a failure.
- State the comparison method. A rendered screenshot comparison is stronger evidence than a static read of templates and SCSS, and the two must never be reported as the same thing.
- Do not evaluate code quality here. That belongs to the code review standard.

---

## Important

Always generate code that follows these standards unless explicitly instructed otherwise.

Do not prioritize speed over code quality.

Consistency, maintainability, and scalability are the primary goals.
